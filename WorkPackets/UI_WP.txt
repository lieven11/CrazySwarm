PURPOSE_BEGIN
This is the canonical implementation backlog for the CrazySwarm operator UI,
simulation backend, mission runtime, digital twin, real-time observer, and the
later real Crazyflie and fleet integrations.

The intended operator product has exactly two execution paths:
SIMULATION runs an uploaded Python mission against a declared physics model.
DIGITAL_TWIN runs the exact same immutable Python artifact against a qualified
real vehicle and a synchronized simulated twin. Replay may exist as an evidence
viewer, but it is not a third mission-execution mode. LIVE without a twin is not
a normal operator workflow. Before a run the dashboard remains observationally
empty and never invents vehicles or telemetry to fill space.

The mission file is the complete mission definition. The UI may upload, name,
select, inspect, and start it, but may not recreate or edit its flight commands,
parameters, or route. Built-in mission choices and dashboard-authored mission
profiles are excluded from the normal operator route.

This document does not authorize real flight. Hardware execution requires a
separate operator action, completed preflight checks, a safe test area, and the
packet-specific gates below. Merely detecting a Crazyradio or Crazyflie must
never arm, take off, or switch the application from SIM to LIVE.
PURPOSE_END

STATUS_BOUNDARY_BEGIN
- Code, screens, mocks, or scaffolding alone do not complete a packet.
- A packet is complete only when every applicable acceptance and verification
  item passes and the completion record contains reproducible evidence.
- Simulation evidence does not qualify real-flight behavior.
- Real-flight evidence does not qualify multi-drone separation or fleet logic.
- UI responsiveness does not qualify command timing or safety behavior.
- A connected vehicle is not an armed vehicle.
- A normal abort-and-land is distinct from emergency motor stop.
- Emergency motor stop is a last-resort, latching motor cutoff and must never
  be presented as an ordinary landing action.
- Browser or renderer failure must not disable backend safety enforcement.
- Hardware-dependent checks remain open until the exact drone, radio, decks,
  firmware, batteries, localization environment, and operator procedure exist.
- Test fixtures, screenshots, and developer stories are never operational data and
  must be isolated from the normal dashboard route and labeled TEST FIXTURE.
- A zero, 100%, healthy badge, vehicle, sensor, or timestamp may not stand in for
  missing data. No observation means unavailable, absent, or not yet observed.
STATUS_BOUNDARY_END

DASHBOARD_PHILOSOPHY_BEGIN
NAME: TRUTH_FIRST_MINIMAL_CONTROL
1. Evidence before decoration. Every displayed value must come from a current
   backend observation, an explicitly running simulation model, a mission plan,
   a saved replay, or versioned configuration.
2. Absence is meaningful. If no source produced a value, omit the metric or show
   a quiet "Not available" state only where the missing value affects a decision.
3. Every value belongs to exactly one visible provenance class: MEASURED_REAL,
   SIMULATED_MODEL, DERIVED, PLANNED, CONFIGURED, REPLAYED, or UNAVAILABLE.
4. SIM never means real. Simulated output appears only after an explicit scenario
   or mission run starts and only for variables the declared model actually computes.
5. A mission-level kinematic or sensor model is not full physical truth. The UI
   names its model and limitations and never implies aerodynamic or RF fidelity.
6. Physical radio link quality, RSSI, battery current, deck readings, IMU samples,
   and localization do not exist in the UI unless hardware measures them or an
   explicitly documented model produces a clearly labeled simulated equivalent.
7. The default screen is mission-first: choose SIMULATION or DIGITAL_TWIN,
   upload/select one Python mission artifact, then run it. The UI has no mission
   command or parameter editor. One primary action is visually dominant.
8. Use progressive disclosure. Idle shows the mission action and configured room;
   running shows only relevant live/simulated state; completed shows evidence and replay.
9. Never display the same fact in two panels. Remove decorative KPIs, redundant
   badges, permanent inspector cards, and explanatory text that does not help a decision.
10. Visual language is monochrome black, off-white, and neutral gray with generous
    space, strong typography, hairline borders, and restrained rounded controls.
    Avoid blue/neon dashboard styling, glow, ornamental gradients, and dense tiles.
11. Reserve red for emergency/fault action and amber for actionable caution. Mode
    identity must use text, icon, structure, and labels rather than decorative color.
12. Developer fixtures may remain for automated tests and a dedicated development
    route, but the normal operator route must never fall back to them.
13. Interface copy is functional. Use short labels, values, and actions; no slogans,
    onboarding prose, filler explanations, or conversational empty-state text.
14. The local simulator/control service is an implementation detail, not an
    operator target. One launcher starts the UI and local API, the UI attaches
    automatically through a same-origin proxy, and no operator copies endpoints
    or authentication tokens. Connect/disconnect controls refer only to an
    explicitly selected vehicle adapter, never to the dashboard's own backend.
DASHBOARD_PHILOSOPHY_END

SYSTEM_INVARIANTS_BEGIN
1. SIM is the default mode at application startup.
2. Hardware discovery may connect for inspection but may not arm or fly.
3. DIGITAL_TWIN requires explicit operator selection, a qualified real adapter,
   a parallel simulated adapter, and preflight approval.
4. Every command carries vehicle ID, command ID, timestamp, source, and mode.
5. Commands are validated by the backend safety supervisor, never only by UI.
6. Mission control sends high-level intent; the browser never runs a flight
   control loop and never directly controls individual motors.
7. Abort-and-land and emergency motor stop are separate commands, styles,
   confirmations, audit records, and backend paths.
8. Stale telemetry, lost heartbeat, invalid localization, critical battery,
   geofence breach, and identity mismatch fail according to explicit policy.
9. SIMULATION, real observations, simulated twin predictions, and REPLAY evidence
   are visibly and structurally distinct.
10. REPLAY cannot emit live commands.
11. Real and simulated vehicles implement one versioned vehicle contract.
12. A mission declares its required capabilities and cannot start if the
    selected vehicle or simulated model does not satisfy them.
13. Every run ends as SUCCEEDED, ABORTED, or FAILED with a reason and evidence.
14. Firmware flashing and unrestricted motor testing remain in official
    CFclient unless separately specified and safety-reviewed in a future packet.
15. A real-versus-simulated deviation is not called ground-truth error unless
    a validated global reference such as Lighthouse, Loco/UWB, or motion
    capture supplies the reference position.
16. The operator dashboard never falls back to mock or fixture telemetry.
17. No mission run means no simulated vehicle state, sensor stream, radio metric,
    battery metric, mission timeline, or fabricated activity state.
18. Missing and zero are different domain values and remain different through
    contracts, APIs, storage, UI models, rendering, exports, and tests.
19. A value unsupported by the selected real or simulated adapter is absent; the
    UI must not infer or substitute a plausible default.
20. The normal dashboard shows one source of truth for each fact and one dominant
    next action; detailed engineering data appears only on request or when relevant.
21. The operator uses one browser origin. Internal API ports and local credentials
    remain server-side and are never required inputs in the normal workflow.
22. Every operator mission is an uploaded immutable Python artifact identified by
    SHA-256. The same hash is recorded for simulation and digital-twin execution.
23. The dashboard never provides a second mission definition through profiles,
    route editing, parameter fields, or built-in takeoff/hover/land choices.
24. Uploaded Python is validated and executed outside the API trust boundary;
    unsupported imports, arbitrary host access, and unbounded code are rejected.
25. Motor, battery, IMU, deck, range, flow, radio, and localization fields appear
    only when measured by hardware or computed by an explicitly named model.
26. The `crazyflie-6dof-v1` simulator is configured but not bench-qualified.
    Raw motor-command Python remains blocked until its safety API and physical
    parameters are separately validated.
SYSTEM_INVARIANTS_END
