## Why WP-01, WP-02, and WP-04 were partially reopened

The backend fleet capabilities were implemented and qualified, but the normal
uploaded-mission path and the fleet operator path were separate when this scope
was reopened. The implementation closeout below records their later unification;
current-tree revalidation is the remaining closeout gate.

The default dashboard starts Fast Sim from `config/worlds/one_drone.yaml`, which
declares `sim01`. The visible fleet control submits a fixed two-drone deployment
containing `cf01` and `cf02`. Fleet preparation correctly fails closed because
the discovered runtime fleet does not match the declared identities. This is an
integration/provisioning defect, not a reason to weaken identity verification.

The current UI also requires a separate `Declare two-drone fleet` workflow while
the normal Play button starts one uploaded mission on one selected vehicle. The
desired product behavior is one mission-driven path:

```text
upload/select Python mission
-> press the existing Play button
-> derive the logical deployment from the immutable mission artifact
-> provision Fast Sim vehicles or verify backend bindings
-> show real preparation states for every required vehicle
-> start only after current telemetry and approved preflight
-> execute one or many child missions through the existing safety/fleet layers
```

There must be no normal-operator switch or button for “single drone” versus
“multi-drone.” Fleet size and roles come from the uploaded mission artifact.

## Development Guide alignment

This reopening implements the guide’s existing architecture rather than adding a
new product mode:

- Mission, fleet manager, vehicle adapter, supervisor, and ground station remain
  separate layers.
- The exact uploaded mission artifact and SHA-256 reach each backend without
  UI-authored mission changes.
- Fast Sim remains the deterministic backend and provisions virtual vehicles from
  a versioned logical deployment.
- Real hardware discovery remains explicit and cannot bind the first aircraft
  found automatically.
- Every vehicle is displayed and monitored independently, including battery,
  readiness, mission state, fault state, and separation.
- Browser code displays state and requests intent; it never runs fleet allocation,
  a flight-control loop, or safety policy.

## Target architecture

```text
immutable uploaded Python
        |
        v
MissionPackage v1/v2 parser
        |
        v
logical DeploymentPlanner
        |
        v
BackendVehicleProvider
  |          |             |
  |          |             +-> real: verify pre-approved physical bindings
  |          +----------------> Isaac/mock: create or verify namespaces
  +---------------------------> Fast Sim: create session-scoped virtual vehicles
        |
        v
FleetPreparation
DECLARE -> DISCOVER/BACKEND INIT -> VERIFY -> CONNECT -> OBSERVE -> PREFLIGHT
        |
        v
ExecutionCoordinator
  |-- one required role  -> MissionRunner
  +-- multiple roles     -> FleetCoordinator -> MissionRunner per role
```

The Python file declares logical mission intent. It never constructs
`FastSimVehicle`, `IsaacSimVehicle`, `CrazyflieVehicle`, a radio URI, an Isaac
prim, a namespace, or simulator parameters.

The world/environment supplies room geometry, obstacles, simulation model, seed,
clock, and fault overlay. It does not fix the number of mission vehicles. The
mission package supplies logical roles, required capabilities, homes, tasks, and
optional reserve roles. The backend provider resolves those logical requirements.

## ACTIVE-WP-01 — Mission-derived deployment and backend provisioning

**Development Guide alignment:** System architecture, Simulation S1/S4, Stages
4–6.

### Outcome

One immutable uploaded Python artifact declares whether the mission needs one,
two, or three logical vehicles. A backend-neutral planner creates a deterministic
deployment, and a backend provider either provisions matching virtual vehicles or
verifies explicitly approved physical bindings.

Existing `async def mission(drone)` artifacts remain valid one-drone missions.
A versioned mission-package extension adds logical roles without putting backend
identifiers in mission code.

### Draft mission-package direction

The syntax is frozen and tested in
[`docs/MISSION_PACKAGE_V2.md`](../docs/MISSION_PACKAGE_V2.md). It is a statically
validated literal declaration plus bounded mission behavior:

```python
MISSION = {
    "schema_version": 2,
    "roles": {
        "zone_a": {
            "logical_vehicle_id": "drone-a",
            "home_m": [-1.0, 0.0, 0.0],
        },
        "zone_b": {
            "logical_vehicle_id": "drone-b",
            "home_m": [1.0, 0.0, 0.0],
        },
    },
}

async def mission(drone):
    # Executed once for each assigned role through the restricted mission worker.
    ...
```

The parser may expose an immutable role/task context, but it must retain the
current source, syntax, command, observation, duration, and process-isolation
budgets. Direct imports, adapter access, filesystem, network, shell, reflection,
and unbounded control flow remain forbidden.

### Canonical startup

```text
1. Validate the immutable uploaded mission package.
2. Derive and hash the logical deployment.
3. Display DECLARED / NOT_OBSERVED placeholders for every required role.
4. Initialize Fast Sim, initialize/load Isaac, or discover approved real devices.
5. Bind and verify every required logical identity.
6. Connect every required vehicle explicitly.
7. Observe enough fresh telemetry to satisfy a source-aware readiness window.
8. Run per-vehicle and fleet preflight.
```

visible. The observation window must be a meaningful readiness rule—such as a
