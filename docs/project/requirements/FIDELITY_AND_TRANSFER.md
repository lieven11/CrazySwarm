# Fidelity and transfer requirements

> Navigation: [requirements index](README.md)

Read when changing Fast Sim, Isaac, physical-flight transfer, model semantics, calibration, or digital-twin claims.

| ID | Requirement | Rationale / verification intent |
|---|---|---|
| `REQ-XFR-001` | Mission intent, geometry, safety limits, causal question, and success criteria must be backend-neutral; model- or adapter-specific inputs must be explicit overlays. | Later digital-twin or physical work should not require redefining what the mission was meant to test. |
| `REQ-XFR-002` | Each submission must declare supported backends and the semantic mapping of its control variables on each backend. There is no silent fallback. | A Fast Sim actuator command cannot be assumed to mean Crazyflie RPM, PWM, or physical thrust. |
| `REQ-XFR-003` | Fast Sim is used for logic, repeatability, authority, and bounded sensitivity. Contact, motor, aerodynamic, sensor, and physical-accuracy claims remain qualified only by the appropriate later stage gate. | Avoids optimizing only for a visually pleasing software simulation. |
| `REQ-XFR-004` | Evidence must state source/model identity and qualification status such as `CONFIGURED_UNQUALIFIED` where appropriate. | Comparisons must not imply more fidelity than the source provides. |
| `REQ-XFR-005` | Physical-reality review reconciles world motion, attitude, body IMU, and every individual motor's requested thrust/applied PWM/thrust/current/headroom/saturation. Forward/lateral acceleration must produce the expected signed differential-actuation response for the declared rotor layout, but configured Fast-Sim agreement remains `CONFIGURED_UNQUALIFIED` until bench/flight evidence closes it. | Distinguishes a real mixer defect from four nearly overlapping plots and prevents software plausibility from becoming a physical qualification claim. |
| `REQ-XFR-006` | A digital-twin session pairs the same canonical mission intent on measured and simulated sides, persists source-time-aligned raw sensor observations and residuals for every available sensor family, retains unavailable/incompatible states, and exposes provenance/model/session identities to review and visualization. It never owns physical safety authority. | Creates a usable sensor-to-visualization data plane without presenting modeled data as measured ground truth. |
| `REQ-XFR-007` | Learning from physical/twin runs creates a bounded, versioned calibration candidate. Promotion requires minimum sample/case coverage, train/holdout separation, improvement on the named residual, non-regression across earlier missions and safety guards, parameter bounds/provenance, and explicit operator acceptance. One run never rewrites safety limits, controller authority, or the active model automatically. | Allows cumulative learning while resisting overfitting and unsafe self-modification. |
| `REQ-XFR-008` | Real-aircraft progression outside the controller-characterization cluster is staged and fail-closed: observation-only startup/sensor checks, props-off bench, contained takeoff/slow hover/land, short point-to-point/return, then smooth and dynamic paths. Every stage reuses the same mission/evidence pipeline and requires the existing bench, flight-entry, operator, observer, containment, permit, and stop gates. Controller-characterization ordering follows the non-blocking rule in `REQ-XFR-010`. | Makes the hardware pipeline ready in software while keeping unperformed physical tests visibly `NOT_RUN` rather than treating readiness as flight qualification. |
| `REQ-XFR-009` | One operator-owned process holds an OS-backed exclusive lease over the physical Crazyradio runtime. Parallel development runtimes are simulation-only, use isolated worktrees/ports, and cannot discover, connect, suspend, command, deploy, or restart physical hardware unless the operator explicitly transfers that authority. Every intentional observer suspension names its owning operation and resumes in bounded cleanup. | Prevents concurrent chats, reloaders, tests, or helper processes from interrupting observation, stealing the radio, timing out the live service, or invalidating physical command state. |
| `REQ-XFR-010` | Implemented Controller characterization & tuning motions in missions B–E remain operator-selectable without software unlocks based on fixture-survey completion, baseline acceptance, earlier mission results, coverage, amplitude progression, or mission-enable flags. Missing geometry, uncertainty, clearance, and baseline evidence remain visible characterization advisories and limit analysis/qualification claims; they do not disable an implemented command. Exact marker/heading/height inputs, command implementability, the selected experiment's controller/estimator identity, and the shared runtime's generic link, supervisor, permit, abort/land, and stop-integrity checks remain authoritative. | Preserves operator control of physical experiments while preventing incomplete characterization from being misrepresented as measured safety, accuracy, or qualification. |
| `REQ-XFR-011` | Physical-radio evidence counts every measured ACK and no-ACK exchange in a bounded window and keeps actual packet loss distinct from retry quality, packet rates, congestion, queue saturation, USB availability, telemetry freshness, and protocol setup. Operator state names the observed failure boundary without claiming a defective component. A hardware claim requires a controlled direct-USB/hub and known-good radio/aircraft substitution matrix. Queue saturation alone does not close an observation link; stale supervision remains bounded, and commands are never replayed after uncertain dispatch. | Prevents cflib queue behavior or incomplete retry statistics from being misreported as hardware packet loss, while preserving fail-closed command semantics and a reproducible hardware-isolation oracle. |
